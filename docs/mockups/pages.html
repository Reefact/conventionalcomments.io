enforce:

A convention doesn't hold on its own.

The extension assists in the editor. The server companion re-checks every comment afterwards and publishes a required status. An unresolved blocking thread stops the merge — whether or not the extension is installed.

Independent tooling. The specification lives on conventionalcomments.org.

on a pull request:
conventional-comments — 2 blocking threads unresolvedRequired · merging is blocked
cc/1 core=1.0.0 mode=enforce blocking=2 fmt=ok fp=7f3c…a91

↓ the author resolves both threads

conventional-comments — all blocking threads resolvedRequired · judged in enforce by core/ 1.0.0
cc/1 core=1.0.0 mode=enforce blocking=0 fmt=ok fp=7f3c…a91
the gap:

An extension can stop a click. It cannot stop an API call.

A browser extension acts client-side only. It cannot stop a comment published through the REST or GraphQL API, a CLI, an IDE, another browser, or a machine that simply doesn't have it installed. Any tool that pretends otherwise is selling you a habit, not a guarantee.

So the toolkit ships two components, with responsibilities stated rather than blurred.

component A

Browser extension

Authoring assistance and real-time validation while a reviewer writes. A label toolbar, keyboard shortcuts, immediate feedback, and a send guard.

Convenience and prevention. Bypassable by construction.

component B

Server companion

Re-reads every comment after the fact, computes “blocking threads resolved”, and publishes a required status check — so a pull request can't be completed with an unresolved blocking comment.

Source of truth. Not bypassable.

the design rule that ties them

A comment judged compliant by the extension is always judged compliant by the server — and conversely.

Both components consume the same core/ package and resolve the same three configuration levels. Parity isn't a promise made in a README; it's what's left when no validation rule exists outside one shared library. When the two do drift — a restrictive change still propagating — the extension notices the fingerprint mismatch, says so, and stops blocking. It never issues a rejection the source of truth wouldn't have issued.

what the check actually measures:

Two criteria, and only two.

criterion 1

Format compliance

Every comment subject to validation parses as label [decorations]: subject. A comment is compliant when it produces no error-severity diagnostic. Warnings are counted, reported — and never a cause of failure.

Gates only when formatSeverity: "error".

criterion 2

Blocking threads resolved

Every thread whose comment resolves to blocking is resolved. Blocking-ness is monotonic: a thread that was blocking stays blocking until it's resolved, or until someone with authority records a decision.

This is the criterion that stops the merge.

Empty review bodies are exempt — an Approve without text would otherwise fail on every approval, with no way to fix it, since you don't edit someone else's review. So are system-generated entries, tool commands, and the authors listed in exemptUsers.

authoring:

What a reviewer actually types

Three keystrokes, not a form. The extension inserts the label, the badge appears, and the comment is validated as it's written.

?i → expands to: issue (blocking, security): the session token is never invalidated The handler keeps the reference after expiry; it has to be dropped from the cache too.
■ label ■ decorations ■ the pivot ■ subject, then discussion
🔨 issue blocking security compliant

Parsed, on both sides, by the same library:

{ "label": "issue", "decorations": ["blocking", "security"], "subject": "the session token is never…", "discussion": "The handler keeps the refer…", "blocking": true }

A comment stops being prose and becomes a record the pipeline can act on. That's the whole point of the convention — and the reason a status check is possible at all.

adoption:

You do not switch this on.

Three modes, in order. Each one is a measurement step before the next becomes defensible.

assist~2 weeks · default The extension helps and diagnoses. The server publishes nothing at all. Nobody is blocked, nobody is measured.
warn2–4 weeks · the measurement step Identical for the reviewer. The server now publishes a status that never fails, whose summary makes non-compliance visible. This is where you get numbers.
enforcepilot repository first The check becomes required. Five prerequisites must hold first — including a written rollback procedure with a named owner.
Prerequisites, rollback, and what warn measures.
privacy:

No comment, code, or diff content ever leaves your browser.

Parsing and validation run locally, in core/, which performs no I/O. No telemetry by default. No authentication token stored. No <all_urls> permission — domains beyond GitHub are requested on demand, with your explicit confirmation.

The exception, stated: your own preferences — interface language, direct shortcuts — sync through chrome.storage.sync when Chrome Sync is on. That's settings, never content.

the one thing that does not work on Azure DevOps

Resolution attribution, and therefore the §6.1 governance rule.

The platform does not tell us who resolved a thread. So the rule that only the comment's author — or a member of resolverOverrideGroup — may resolve it cannot be enforced there. Resolutions are honoured, and the status carries resolution-unattributed on every evaluation, so nobody has to discover this from a support ticket. It is stated here because a tech lead choosing between platforms deserves to know before adopting, not after.

permissions:

Out of the box, it runs on github.com and nowhere else.

There is no <all_urls> in the required permissions, and one single content-script match. Azure DevOps, a GitHub Enterprise Server instance, an enterprise configuration host — each is an optional host permission, requested on demand and granted by you, then tagged with its platform on the options page.

Two required permissions in total: storage for your own preferences, and scripting. No authentication token is stored. The extension CSP is script-src 'self' — no remote code can be loaded, which the packaging workflow verifies on every push.

manifest.json:
"manifest_version": 3, "permissions": ["storage", "scripting"], "optional_host_permissions": ["https://*/*"], "content_scripts": [{ "matches": ["https://github.com/*"], // ← the only one "js": ["content.js"], "run_at": "document_idle" }], "content_security_policy": { "extension_pages": "script-src 'self'; object-src 'self'" }
enterprise server:

One open item, and a failure mode chosen on purpose

Which GitHub Enterprise Server DOM generations to target is still being settled. Selectors are written as chains with fallbacks, and covered by a multi-version smoke test.

when a selector stops matching

The extension disables its own zone. It never touches the page it no longer understands.

Selector degradation is a designed behaviour, not an accident: when the platform DOM moves under it, the affected zone goes quiet and the reason is reported, rather than the extension writing into an element it has misidentified. You lose assistance on that zone. You never lose the ability to use GitHub — and the server companion keeps judging, because it never depended on the DOM in the first place.

Labels & decorations

Thirteen labels, three known decorations, and one precedence table that decides whether a comment blocks a merge. This page is the reference for all three.

The grammar

Every validated comment starts with a prefix line. Everything after the first blank line is discussion, and is never parsed.

label [decorations]: subject [discussion]
■ label — required, lowercase ■ decorations — optional, comma-separated, in parentheses ■ the pivot

Casing is corrected rather than rejected: Issue: raises W-CASE, a warning that ships with a one-click fix.

The thirteen labels

Ten are enabled by default. Three — typo, polish, quibble — ship disabled; they're expressive variants of todo, suggestion and nitpick, and a repository enables them if it wants them.

LabelWhat it saysBlockingKey
🎉 praiseHighlights something done well.by decoration?pr
🔍 nitpickA trivial preference, with nothing at stake.never?ni
💡 suggestionA reasoned proposal for improvement.by decoration?su
🔨 issueA problem identified. Ideally paired with a suggestion.by default?i · ?ib
📌 todoA small but necessary change.by default?to
❓ questionA request for clarification on an uncertain point.by decoration?que
💭 thoughtAn idea that came up in review, with no action requested.never?th
🧹 choreA side task to complete before acceptance.by default?ch
📝 noteInformation worth knowing.never?no
🏁 decisionRecords the choice not to address a point, and says why.never?de
🔤 typoA typing mistake.off by default?ty
✨ polishA finishing improvement.off by default?po
🫶 quibbleA debatable detail.off by default?qui

Colours and icons are cosmetic by design: they're excluded from the configuration fingerprint and from the enterprise floor, so they can never make two verdicts diverge, and can never be locked by an administrator.

decision — the label this toolkit adds

decision is not in the original specification. It exists because enforce without a release valve is a trap: a blocking thread whose author has gone on leave would hold a pull request forever, with no recourse.

it is judged where nothing else is

The one label read in an unvalidated zone

Thread replies aren't validated by default (validateReplies: false). A reply whose resolved label is decision is picked up anyway — otherwise the valve would only work in repositories that had already opted into validating replies.

and it must be justified at length

E-DECISION-SUBJECT, an error — not a warning

A decision reply must reach minDecisionSubjectLength — 20 characters by default — and that's the only length threshold that applies to it. Closing a blocking thread costs you a sentence explaining why. “wontfix” doesn't clear the bar.

decision: out of scope for this PR, debt tracked in PROJ-142 Agreed with the platform team on 3 Sep: the cache rewrite lands in Q4 and this handler is deleted with it.

Who may record one is governed, not open: resolverOverrideGroup names the group whose members can override a resolution. Designating it is a hard prerequisite for enforce — an empty group makes both release valves inert at once.

Decorations

Decorations qualify a label. Three are known to the product; free decorations are allowed by default and carry meaning for humans without changing the verdict.

DecorationForcesMeaning
blockingblockingMust be resolved before the subject under review is accepted.
non-blockingnon-blockingMust not prevent acceptance.
if-minornon-blockingResolve only if the change turns out to be trivial. The author decides.
security test uxnothingFree decorations. Rendered, counted, indexed — never a verdict input. An organization defines its own.

suggestion and question written with no decoration at all raise W-MISSING-DECORATION: they're the two labels whose blocking intent a reader genuinely cannot guess.

Precedence — how blocking is resolved

Five rules, evaluated in order. The first that matches decides. This table is the whole of it; there is no other input.

#ConditionResultDiagnostic
1Label is alwaysNonBlocking, yet a decoration forces blockingfalls back to blockingByDefaultE-CONFLICT
2One decoration forces blocking and another forces non-blockingfalls back to blockingByDefaultE-CONFLICT
3A decoration forces blockingblocking—
4A decoration forces non-blockingnon-blocking—
5No forcing decorationthe label's blockingByDefault—
why a conflict still produces a verdict

Rules 1 and 2 raise an error, but they don't refuse to answer. A contradictory comment still resolves — to the label's default — because leaving a thread in an undefined blocking state would make criterion 2 unanswerable, and the pull request unmergeable for a reason nobody could act on.

Diagnostics

Fifteen codes. Errors make a comment non-compliant, and only gate a merge when the repository sets formatSeverity: "error". Warnings are counted and surfaced, never a cause of failure. Any code can be re-levelled — or silenced — per repository through severities.

errorraised when
E-NO-LABELNo prefix line at all.
E-MALFORMED-PREFIXA prefix that nearly parses, but doesn't.
E-UNKNOWN-LABELLabel not enabled in this repository.
E-EMPTY-SUBJECTLabel and colon, then nothing.
E-DECORATION-SYNTAXParentheses or separators malformed.
E-UNKNOWN-DECORATIONUnknown, and free decorations are off.
E-CONFLICTPrecedence rule 1 or 2.
E-DECISION-SUBJECTA decision that doesn't say why.
warningraised when
W-CASEWrong casing. Ships a fix.
W-DECORATION-STYLESpacing or order off. Ships a fix.
W-SUBJECT-TOO-SHORTUnder 5 characters.
W-SUBJECT-TOO-LONGOver 120 characters.
W-MISSING-DECORATIONsuggestion or question, undecorated.
W-NO-DISCUSSIONA blocking comment with no discussion.
W-NOT-BLOCKABLEBlocking, in a zone that can't hold that state.
calibration

A short subject is a warning on purpose, at a low threshold.

Five characters, and never an error. A too-short subject isn't a serious defect, and making it a blocking one pushes people to work around the rule rather than apply it. Enforcement that punishes small things loses the argument for the large ones.

Adoption: assist → warn → enforce

Turning the convention into a merge requirement is an operational decision, not a configuration flag. This page is the sequence, the prerequisites, and the way back out.

The sequence

week 0–2assistInstall, let people use it. No status published, nothing measured.
week 2–6warnServer publishes a never-failing status. You now have a compliance rate.
thenenforceOne pilot repository. Prerequisites met, rollback rehearsed.
afterrolloutWidened repository by repository, on the pilot's numbers.
ModeExtension doesServer publishesEffect on a PR
offNothing.Nothing.None.
assistAssists and diagnoses. Never blocks.Nothing.None.
warnIdentical to assist.A status that never fails, whose summary shows non-compliance.Visible, never blocking.
enforceBlocks sending a non-compliant comment.A required status that fails on an unresolved blocking thread.Merge refused.

assist and warn are identical for the reviewer. What separates them is entirely server-side — which is what makes warn a pure measurement step, with no change in anyone's daily experience to confound the numbers.

Prerequisites for enforce

Three hold everywhere. Two more apply on Azure DevOps.

  • 1resolverOverrideGroup is designatedWithout an authorized group, both release valves are inert at once — no decision, no PR exemption — and a thread whose author is unavailable blocks the pull request with no recourse. The server emits a config-warning on every evaluation of an enforce repository whose resolved group is empty.
  • 2The rollback procedure is written, and its owner is namedNot “someone will figure it out”. A named person with access to the organization configuration channel and to the server's admin endpoint. See below.
  • 3The check is required, and bypass is disabledGitHub: Require status checks to pass on conventional-comments, plus Do not allow bypassing the above settings. Azure DevOps: a Status checks branch policy on conventional-comments/compliance, set to Block rather than Warn. Without the second half, the guarantee doesn't hold for administrators.
  • 4Azure DevOps — label provenance is established, or the fallback is in placeThe exemption fallback is implemented end to end: admin entry point, persisted active exemption, label posted by the server. Until a provenance source exists, the fallback is what you're running.
  • 5Azure DevOps — detection latency meets the 60 s targetEither an event channel is established, or reconcileIntervalSeconds is set to 60 or below. The server emits a config-warning if the interval exceeds 60 s in enforce.

Rollback

the one thing to get right

The fallback is warn. It is not off, and it is not assist.

In warn, the server keeps publishing a status that never fails — which unblocks every pull request immediately, without touching branch protection. assist and off publish nothing at all: dropping to them from enforce leaves a required check with no status, and blocks every pull request in the organization until protection is removed repository by repository. Reaching for off in an incident is how a rollback becomes a second incident.

  • 1Set mode to warn in the organization configurationA relaxation is a widening change: it applies to already-open pull requests without waiting for them to close.
  • 2Wait — cache invalidation is automaticThe organization document is probed every 60 s, bypassing the cache; the whole configuration cache is invalidated as soon as the observed mode is softer than the previous one. POST /admin/cache/invalidate forces it to the second if you don't want to wait.
  • 3Verify a green warn status on a witness pull requestConfirm on a real PR, not in the configuration.

The target the specification sets: a full rollback across every repository, in minutes, with no per-repository intervention. If your procedure needs a repository loop, it isn't the procedure.

What warn measures

Six indicators. The first two decide whether enforce is defensible; the last one is the abuse signal.

IndicatorReads as
complianceRateShare of human comments with no error-severity diagnostic. The number enforce rests on.
warningRateShare carrying warnings only. High and stable is fine — these never block.
labelDistributionCounts per label. A distribution collapsed onto note and nitpick means people are dodging blocking labels.
serviceAccountShareShare of comments from bots. Tells you whether toolCommands and exemptUsers are set correctly.
totalHumanCommentsThe denominator. A rate on twelve comments is not a measurement.
decisionsInBlockingThreadsHow often the release valve is used. Rising steadily means enforce is being routed around rather than met — read it before widening the rollout.

The configuration, per phase

The switch is a single key in the organization document. Everything else stays as it is.

// organization configuration — the tipping point { "version": 1, "mode": "warn", // assist → warn → enforce "resolverOverrideGroup": ["acme/tech-leads"], "formatSeverity": "warn", // criterion 1 does not gate "exemptUsers": ["dependabot[bot]", "github-actions[bot]"], "toolCommands": ["/*", "@dependabot", "@renovate"], "server": { "gracePeriodSeconds": 900, "reconcileIntervalSeconds": 900 } }
upgrade note

toolCommands is empty by default. Slash commands used to be exempted through a built-in list; that list is gone. In enforce, a bare /rebase is now rejected like any other comment until the repository declares it. Adding "/*" restores the exemption and widens it to every slash command.
